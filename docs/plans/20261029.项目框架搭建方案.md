## 0. 一页结论

| 维度 | 默认方案 | 结论 |
| --- | --- | --- |
| 代码组织 | Monorepo：`frontend/` + `backend/` + `deploy/` + `docs/` | 单人/小团队最省心，前后端联调、版本对齐、CI 配置都在一个仓库 |
| 前端 | Vue 3 + TypeScript + Vite + Vue Router + Pinia + Element Plus | 管理后台/业务系统的主流组合，生态成熟 |
| 后端 | 测试期 Java 17 + Spring Boot 3.5.x；正式上线 Java 25 + Boot 4.1.x | 单体优先，按功能分包；规模上来再拆 |
| 数据层 | MySQL 8.4 LTS + MyBatis-Plus + Flyway | SQL 可控、迁移可追踪；Redis 8 做缓存/会话/限流 |
| 接口 | REST + `/api/v1` + 统一响应 + OpenAPI | 前后端契约清晰，可生成 TS 类型 |
| 认证 | Spring Security + JWT + HttpOnly Refresh Cookie | 无状态、易扩展；刷新令牌可撤销 |
| 部署 | 单台 Ubuntu 24.04 + Docker Compose + 宿主机 Nginx + Certbot | 当前 CentOS 8.2 需先重装；美国实例无需备案 |
| CI/CD | GitHub Actions → GHCR → SSH 部署 | 免费、配置简单；国内服务器可换阿里云 ACR + 云效 |
| 监控备份 | Actuator 健康检查 + 外部拨测 + 每日 mysqldump + 异机备份 | 先覆盖“挂了知道、数据能恢复”两条底线 |

**三条原则：**

1. **先跑通再优化**：第一版不引入 K8s、微服务、消息队列；单机 Docker Compose 足够支撑早期业务。
2. **配置与密钥外置**：代码仓库不出现任何密码、Token、证书私钥；生产配置全部走环境变量。
3. **部署必须可回滚**：镜像按 commit SHA 打不可变标签，前端按 release 目录切换，数据库迁移遵循“向前兼容”。

## 2. 总体架构

### 2.1 运行拓扑（单机起步）

```text
                         Internet
                            │
                     HTTPS 443 / HTTP 80
                            │
                  ┌─────────▼─────────┐
                  │   Nginx (宿主机)   │
                  │  TLS / Gzip / 限流 │
                  └──────┬──────┬─────┘
                         │      │
            静态资源      │      │  /api/ 反向代理
        /var/www/demo/current   │
                         │      ▼
                         │  127.0.0.1:8080
                         │  ┌──────────────────┐
                         │  │ Spring Boot 容器  │
                         │  │  /api/v1/...      │
                         │  └───┬──────────┬───┘
                         │      │          │
                         │  ┌───▼────┐ ┌───▼────┐
                         │  │ MySQL  │ │ Redis  │
                         │  │ 8.4    │ │ 8.x    │
                         │  └────────┘ └────────┘
                         │   （仅 Docker 内网，不暴露公网）
                         │
        CI/CD：GitHub Actions ──构建/测试──▶ GHCR ──SSH──▶ 服务器
```

**请求链路：**

1. 浏览器访问 `https://gmingli.top`，Nginx 返回 `index.html` 与静态资源。
2. 前端请求 `https://gmingli.top/api/v1/...`，Nginx 反代到 `127.0.0.1:8080`。
3. Spring Boot 通过 Docker 内网访问 `mysql:3306`、`redis:6379`。
4. MySQL/Redis 不映射宿主机端口，公网无法直连。

### 2.2 环境划分

| 环境 | 用途 | 前端 | 后端 | 数据 |
| --- | --- | --- | --- | --- |
| local | 本地开发 | Vite `5173` | `8080`，`local` profile | Docker 起 MySQL/Redis |
| staging（可选） | 预发/验收 | 独立域名或端口 | 独立容器/库 | 独立数据库 |
| prod | 生产 | Nginx 静态托管 | Docker 容器 | 独立数据库 + 每日备份 |

> 初期可以只保留 local + prod。团队超过 2 人或发布频率提高后，再加 staging；staging 可与 prod 同机不同端口/库，但资源要留余量。

### 2.3 为什么是 Monorepo + 单体后端

- 前后端接口改动在一个 PR 内完成，CI 一次跑完，不会出现“前端等了后端三天”的版本错位。
- 单体后端按功能分包（`auth`、`user`、`system`），比一开始拆多模块更省心；模块边界靠包结构和代码评审约束。
- 等出现明确的独立部署/独立扩容需求，再按包拆服务，成本最低。

### 4.3 接口规范

**路径：**

- 全局 context-path：`/api`
- 业务版本：`/v1`
- 最终形态：`/api/v1/users`、`/api/v1/auth/login`
- Nginx 只代理 `/api/`，不做路径重写，避免“到底谁在改写 URL”的排查成本。

**方法：**

| 操作 | 方法 | 示例 |
| --- | --- | --- |
| 查询列表 | GET | `GET /api/v1/users?page=1&size=20` |
| 查询详情 | GET | `GET /api/v1/users/{id}` |
| 创建 | POST | `POST /api/v1/users` |
| 全量更新 | PUT | `PUT /api/v1/users/{id}` |
| 部分更新 | PATCH | `PATCH /api/v1/users/{id}/status` |
| 删除 | DELETE | `DELETE /api/v1/users/{id}` |

**统一响应：**

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "traceId": "b7c2f0d4e1a94f6c",
  "timestamp": "2026-10-29T10:00:00+08:00"
}
```

- `code = 0` 表示成功；非 0 为业务错误码。
- HTTP 状态码同时保持语义：400 参数错误、401 未认证、403 无权限、404 不存在、409 冲突、500 系统错误。
- 错误码分段：`1xxxx` 通用、`2xxxx` 认证/权限、`3xxxx` 业务。示例：`20001` 用户名或密码错误，`20002` 账号被锁定。
- 分页：`{"list":[],"total":0,"page":1,"size":20}`；`size` 上限 100，排序字段走白名单。
- 时间：统一 ISO 8601 带时区；内地业务建议 MySQL、JVM、JDBC、Jackson 全链路统一 `Asia/Shanghai`，避免时区换算错误。若未来面向多时区用户，再整体切 UTC 并做数据迁移，不要局部混用。
- Long 类型 ID 在 JSON 中序列化为字符串，避免 JS `Number` 精度丢失。
- 金额用 `BigDecimal`/`DECIMAL`，禁止 `double`。

### 4.4 统一异常处理

`@RestControllerAdvice` 处理四类异常：

1. `BusinessException`：业务可预期错误，返回对应 code 与 message，HTTP 400/409。
2. `MethodArgumentNotValidException` / `ConstraintViolationException`：参数校验，拼接字段错误，HTTP 400。
3. `AccessDeniedException`：无权限，HTTP 403。
4. `Exception`：兜底，记录 error 日志 + traceId，返回“系统繁忙”，HTTP 500，不把堆栈返回给前端。

**日志要求：**

- 业务异常 `warn`，系统异常 `error`，都要带 `traceId`、用户 ID、请求路径。
- 不打印密码、Token、身份证、手机号等敏感信息；必要时脱敏。
- 生产日志级别 `INFO`，排查时可临时调 `DEBUG`，排查后恢复。

### 4.5 认证与授权

**令牌设计：**

| 令牌 | 存储 | 有效期 | 说明 |
| --- | --- | --- | --- |
| Access Token | 前端内存（Pinia），请求头 `Authorization: Bearer` | 30 分钟 | JWT，含 `sub`、`roles`、`perms`、`jti`、`exp` |
| Refresh Token | HttpOnly + Secure + SameSite=Lax Cookie | 7 天 | 随机不透明串，Redis 存储，可撤销、可轮换 |

**流程：**

1. `POST /api/v1/auth/login` 校验账号密码（BCrypt），签发 access + refresh。
2. 前端把 access 放内存，刷新令牌由浏览器自动携带。
3. access 过期返回 401，前端调用 `POST /api/v1/auth/refresh`，成功后重放原请求；并发 401 只刷新一次，其余请求排队。
4. 登出删除 Redis 中的 refresh，并清除 Cookie。
5. 修改密码/禁用账号时，删除该用户所有 refresh，access 依靠短有效期自然失效。

**权限模型：**

- `sys_user` / `sys_role` / `sys_permission` / `sys_user_role` / `sys_role_permission`。
- 后端方法级鉴权：`@PreAuthorize("hasAuthority('user:list')")`。
- 前端按钮级：`v-perm="'user:add'"`；路由 `meta.perm` 控制菜单显示。
- 默认拒绝：Security 配置里只放行登录、刷新、健康检查、静态资源，其余全部认证。

**安全细节：**

- JWT 密钥至少 32 字节随机值，放环境变量 `APP_JWT_SECRET`，定期轮换（轮换会导致旧 token 失效，安排在低峰）。
- 登录失败 5 次锁定 15 分钟（Redis 计数），防暴力破解。
- 密码 BCrypt（strength 10+），禁止明文/可逆加密。
- 生产环境关闭 Swagger UI 与 API Docs。
- 如前后端不同域，才配置 CORS 白名单；同域部署不需要 CORS。

### 4.6 数据库与 Flyway

**表设计约定：**

- 引擎 InnoDB，字符集 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`。
- 主键 `bigint unsigned auto_increment`；对外 JSON 转字符串。
- 公共字段：`created_at`、`updated_at`、`created_by`、`updated_by`、`deleted`、`version`。
- 逻辑删除用 `deleted`（0/1），唯一索引要包含 `deleted` 或改用状态字段，避免删除后无法重建同名记录。
- 金额 `DECIMAL(18,2)`；状态用 `tinyint` + 枚举常量。
- 默认不建物理外键，靠应用层保证 + 索引；强一致场景再评估。
- 索引按真实查询建，避免“每个字段都加索引”；联合索引注意最左前缀。

**Flyway：**

```text
src/main/resources/db/migration/
├── V1__init_schema.sql
├── V2__init_data.sql
└── V3__add_user_avatar.sql
```

- `spring.flyway.enabled=true`，`validate-on-migrate=true`，`clean-disabled=true`。
- 已执行的迁移文件禁止修改，只能新增版本。
- 生产迁移随应用启动执行；单实例部署，不存在并发迁移。
- 破坏性变更（删列/改类型/大批量更新）必须走“扩展-收缩”：
  1. 先加新列/新表，双写或兼容读；
  2. 发布代码；
  3. 确认无回滚需求后，再删旧列。
- 高风险发布前先备份；迁移失败时应用起不来，靠备份恢复，不能只靠回滚镜像。

### 5.3 路由与权限

- 路由 `meta`：

```ts

  path: '/users',
  component: () => import('@/views/user/UserListView.vue'),
  meta: { title: '用户管理', requiresAuth: true, perm: 'user:list' }
}
```

- 全局守卫：
  1. 白名单（`/login`、`/403`、`/404`）直接放行。
  2. 无 access token 时尝试静默刷新（HttpOnly Cookie）；失败跳登录并带 `redirect`。
  3. 有 token 但无用户信息时拉 `/auth/me`。
  4. 校验 `meta.perm`，无权限跳 `/403`。
  5. 设置页面标题。
- 菜单根据路由表 + 权限过滤生成，避免后端菜单与前端路由两套数据源。
- 按钮权限用 `v-perm` 指令；无权限时移除 DOM，而不是仅 `disabled`。

### 5.4 请求层

```ts
// src/utils/request.ts
import axios from 'axios'
import { useAuthStore } from '@/stores/auth'

const service = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL,
  timeout: 15000,
  withCredentials: true,
})

service.interceptors.request.use((config) => {
  const auth = useAuthStore()
  if (auth.accessToken) {
    config.headers.Authorization = `Bearer ${auth.accessToken}`
  }
  config.headers['X-Request-Id'] = crypto.randomUUID()
  return config
})
```

响应拦截器要处理：

- `code === 0`：返回 `data`。
- 401：只触发一次 refresh，其余请求排队；刷新失败清理状态并跳登录。
- 403：提示无权限，不跳登录。
- 4xx 业务错误：用后端 `message` 弹提示。
- 5xx/网络错误：统一“服务暂时不可用”，上报 Sentry（可选）。
- 文件下载：单独封装 `responseType: 'blob'`，从 `Content-Disposition` 取文件名。

### 7.1 服务器规格

| 场景 | 建议 | 说明 |
| --- | --- | --- |
| 云服务器（后续） | 2 vCPU / 2 GiB / 40 GiB | 当前不用于部署；生产前升级或换机 |
| 最小可用 | 2 vCPU / 4 GiB / 40 GiB SSD | 应用 + MySQL + Redis 同机，适合早期低并发 |
| 推荐 | 4 vCPU / 8 GiB / 80 GiB SSD | 留出 JVM、MySQL buffer pool、日志、镜像空间 |
| 带宽 | 3~5 Mbps | 静态资源大或用户多时上 CDN/OSS |

- 开启云盘快照/自动快照，保留 7 天。
- 后续迁移到 Linux 时，使用 Ubuntu 24.04 LTS，时区 `Asia/Shanghai`；当前 CentOS 8.2 不执行。
- 生产服务器不要跑开发工具、不要放无关服务。
- **2 GiB 实例不要在服务器上跑 `mvn package` / `pnpm build`**，构建全部放 CI；服务器只负责拉镜像和运行容器。

### 7.1.1 2 GiB 云服务器调优（后续迁移时）

| 组件 | 配置 | 说明 |
| --- | --- | --- |
| Swap | 2 GiB | 防止瞬时 OOM；不能替代内存 |
| JVM | `-Xms256m -Xmx512m` | 通过 `JAVA_TOOL_OPTIONS` 注入 |
| MySQL | `innodb_buffer_pool_size=256M`、`max_connections=50`、`performance_schema=OFF` | 降低常驻内存 |
| Redis | `maxmemory 128mb`、`allkeys-lru` | 缓存/令牌可能被淘汰，接受测试期风险 |
| Docker | 日志轮转 20m × 5 | 防止日志占满磁盘 |

监控命令：

```bash
free -h
docker stats --no-stream
dmesg -T | grep -i -E 'oom|killed process'
```

> 如果频繁 OOM，优先升级到 4 GiB，而不是继续压缩 JVM 堆；堆太小会导致频繁 GC、接口变慢。

### 7.3 域名与备案

**当前方案（云服务器 A 记录）：**

| 记录 | 类型 | 值 | TTL |
| --- | --- | --- | --- |
| `@` | A | `43.110.27.119` | 600 |
| `www` | A | `43.110.27.119` | 600 |
| `api`（可选） | A | `43.110.27.119` | 600 |

> 当前实例是美国硅谷，无需备案；A 记录直接指向 `43.110.27.119`。如果以后换服务器，TTL 600 便于切换。

**中国内地服务器：**

- 域名需完成实名认证，再通过云厂商提交 ICP 备案；备案需要服务器（部分厂商要求包月 ≥ 3 个月）和备案服务码。
- 备案周期通常 7~20 个工作日；未备案时 80/443 可能被云厂商拦截。
- 备案通过后 30 日内完成公安联网备案，页脚展示备案号并链接工信部。
- 备案期间可先用香港/海外节点开发，但不要用未备案域名对内地公网提供服务。

**香港/海外服务器：**

- 不需要 ICP 备案，但内地访问延迟高、线路不稳定；无法使用内地 CDN（需备案）。
- 若主要用户在内地，优先备案 + 内地服务器。

**美国云服务器（后续直连时）：**

- 无需备案；后续直连时可把 `gmingli.top` 解析到 `43.110.27.119`。
- 内地访问延迟通常 150ms+，API 首包和静态资源都会变慢；主要用户在内地时，优先考虑香港/新加坡节点或加 CDN。
- 使用 Cloudflare 等 CDN 时，先保持 DNS only（灰云）完成证书签发和联调，再决定是否开代理；开代理后注意回源 IP、证书模式和限流取真实 IP。
- 跨境数据合规（个人信息出境、行业监管）需自行评估，必要时咨询法务。

### 7.6 Nginx 配置

`/etc/nginx/snippets/security-headers.conf`：

```nginx
add_header X-Content-Type-Options nosniff always;
add_header X-Frame-Options SAMEORIGIN always;
add_header Referrer-Policy strict-origin-when-cross-origin always;
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
```

`/etc/nginx/conf.d/demo.conf`：

```nginx
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=20r/s;

server {
    listen 80;
    server_name gmingli.top www.gmingli.top;

    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }

    location / {
        return 301 https://$host$request_uri;
    }
}

server {
    listen 443 ssl http2;
    server_name gmingli.top www.gmingli.top;

    server_tokens off;
    client_max_body_size 20m;

    ssl_certificate     /etc/letsencrypt/live/gmingli.top/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/gmingli.top/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;
    ssl_prefer_server_ciphers off;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;

    root /var/www/demo/current;
    index index.html;

    gzip on;
    gzip_comp_level 6;
    gzip_min_length 1024;
    gzip_vary on;
    gzip_types text/plain text/css text/javascript application/json application/javascript application/xml image/svg+xml;

    # Nginx add_header 只在当前层级无 add_header 时继承；
    # 带自定义 Cache-Control 的 location 需要再次 include。
    include snippets/security-headers.conf;

    # 前端静态资源：带 hash，长缓存
    location /assets/ {
        include snippets/security-headers.conf;
        add_header Cache-Control "public, max-age=31536000, immutable" always;
        try_files $uri =404;
    }

    # index.html 不缓存，保证发布后立即生效
    location = /index.html {
        include snippets/security-headers.conf;
        add_header Cache-Control "no-store" always;
    }

    # SPA 路由回退
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 健康检查放行，其余 actuator 禁止
    location = /api/actuator/health {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /api/actuator/ {
        deny all;
    }

    # API 反向代理（context-path 已是 /api，不做路径重写）
    location /api/ {
        limit_req zone=api_limit burst=40 nodelay;
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Request-Id $request_id;
        proxy_read_timeout 60s;
        proxy_send_timeout 60s;
    }
}
```

检查与重载：

```bash
sudo nginx -t && sudo systemctl reload nginx
```

> 如果后续上 CDN，需要配置 `set_real_ip_from` 与 `real_ip_header`，否则限流会把 CDN 回源 IP 当成用户 IP。

### 7.7 HTTPS（Let's Encrypt + Certbot）

首次签发前，Nginx 先只保留 80 端口的 server 块（含 ACME location），确保 `http://gmingli.top/.well-known/acme-challenge/` 可访问。

```bash

  -w /var/www/certbot \
  -d gmingli.top -d www.gmingli.top \
  --email 932062373@qq.com \
  --agree-tos --no-eff-email
```

签发成功后，再启用 443 server 块并 `nginx -t && systemctl reload nginx`。

### 7.9 数据备份

`deploy/scripts/backup-db.sh`：

```bash
#!/usr/bin/env bash
set -euo pipefail

APP_DIR=/opt/demo
BACKUP_DIR=${APP_DIR}/backups
STAMP=$(date +%F_%H%M)
mkdir -p "$BACKUP_DIR"

set -a
. "${APP_DIR}/.env"
set +a

docker compose -f "${APP_DIR}/docker-compose.prod.yml" exec -T \
  -e MYSQL_PWD="${MYSQL_PASSWORD}" mysql \
  mysqldump -u"${MYSQL_USER}" \
  --single-transaction --routines --triggers --events \
  "${MYSQL_DATABASE}" | gzip > "${BACKUP_DIR}/db_${STAMP}.sql.gz"

# 本地保留 30 天
find "$BACKUP_DIR" -name 'db_*.sql.gz' -mtime +30 -delete

# 异地备份（示例：rclone 到 OSS/S3）
# rclone copy "${BACKUP_DIR}/db_${STAMP}.sql.gz" oss:demo-backup/mysql/
```

crontab（deploy 用户）：

```cron
0 3 * * * /opt/demo/backup-db.sh >> /opt/demo/backups/backup.log 2>&1
```

要求：

- 每日全量备份，保留 30 天；每周至少一次异机/对象存储备份。
- 每季度做一次恢复演练：在临时库 `gunzip | mysql` 导入，核对关键表行数。
- Redis 只做缓存/会话时不备份；如存业务数据，开启 AOF 并纳入备份。
- 上传文件若存本地 volume，必须一并备份；更推荐直接存 OSS/MinIO。

### 7.10 监控告警

**最小可用：**

- 外部拨测：UptimeRobot / 阿里云云监控 / Better Stack，监测 `https://gmingli.top/api/actuator/health`，期望返回 `"status":"UP"`，间隔 1~5 分钟。
- 云监控：CPU、内存、磁盘、带宽；磁盘 > 80% 告警。
- 证书到期：Certbot 自动续期 + 拨测 HTTPS 证书剩余天数。
- CI/CD 失败通知：GitHub 邮件 / 钉钉/飞书/Slack Webhook。
- 应用错误：Sentry（前后端）可选，但强烈建议。

**进阶（有预算/人力再做）：**

- Prometheus + Grafana + node_exporter + mysqld_exporter。
- Loki/Promtail 或云日志服务采集容器日志。
- 告警规则：5xx 比例、P95 延迟、健康检查失败、备份失败、容器重启次数。

### 7.11 安全基线

- SSH：仅密钥、禁 root、fail2ban、非必要不开新端口。
- Docker：`deploy` 用户加入 `docker` 组等同于 root 权限（可挂载宿主机根目录），服务器只跑本项目容器，不与他人共用；安全要求高时用 rootless Docker 或受限 sudo 包装。
- 数据库：强随机密码、应用专用账号、仅内网、定期轮换。
- Redis：`requirepass`、仅内网、禁用危险命令（`rename-command FLUSHALL ""` 可选）。
- 应用：HTTPS、HSTS、CSP（按需）、登录限流、上传大小/类型限制、SQL 参数化。
- 密钥：`.env` 权限 600；GitHub Secrets；不写进镜像、不写进日志。
- 依赖：Dependabot/Renovate 每周更新；镜像 Trivy 扫描；GitHub Actions 按 SHA 固定版本。
- 审计：登录、权限变更、关键业务操作留痕。
- 合规：涉及个人信息/等保/行业监管时，另行评估数据留存、加密、脱敏与审计要求。

## 8. 自动化部署

> **当前阶段（CentOS 8.2）**：使用 8.14 的 “jar + systemd” 部署，不需要 Docker、GHCR、镜像仓库。8.1~8.13 的 Docker/Compose/镜像流程是正式上线迁移到新服务器后的方案，当前不执行。

### 8.1 目标流水线

```text
git push
   │
   ├─ PR：lint / typecheck / unit / build / backend verify
   │
   └─ main/tag：
        1. 构建并测试
        2. 构建后端镜像，打 sha-<commit> 标签，推送镜像仓库
        3. 构建前端 dist
        4. SSH 到服务器：上传前端 release → 拉镜像 → 重启后端
        5. 健康检查（失败自动回滚）
        6. 通知结果
```

**自动化部署的 4 个前提（代码层面）：**

1. 应用无状态：会话/文件不依赖本机；JWT 无状态，上传走对象存储。
2. 配置外置：数据库、Redis、密钥全部环境变量注入。
3. 健康检查可用：`/api/actuator/health` 能反映真实就绪状态。
4. 数据库迁移可重复/向前兼容：Flyway 随应用启动，破坏性变更分两次发布。

### 8.2 方案选型

| 方案 | 适用 | 优点 | 注意 |
| --- | --- | --- | --- |
| GitHub Actions + GHCR | 代码在 GitHub，服务器在海外/网络可达 | 免费额度足、生态好、配置简单 | 国内服务器拉 GHCR 可能慢/不稳定 |
| 阿里云云效 Flow + ACR | 服务器在阿里云/国内 | 拉取快、备案/云资源一体化 | 绑定阿里云 |
| GitLab CI + Registry | 自建/企业 GitLab | 一体化、可控 | 需维护 Runner |
| Gitee Go + 自建 Registry | 代码在 Gitee | 国内访问快 | 生态与镜像仓库需额外配置 |
| Jenkins | 已有 Jenkins 的团队 | 灵活、插件多 | 维护成本高，不推荐从零搭 |

> 默认按 **GitHub Actions + GHCR** 写；如果服务器在中国内地，优先把镜像推到 **阿里云 ACR**，CI 仍可用 GitHub Actions，只改 `IMAGE_REPO` 与登录方式。

### 8.5 CI 工作流（PR 校验）

`.github/workflows/ci.yml`：

```yaml
name: ci

on:
  pull_request:
  push:
    branches: [main]

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

jobs:
  frontend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: frontend
    steps:

      - uses: pnpm/action-setup@v4
        with:
          version: 12
          run_install: false
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: pnpm
          cache-dependency-path: frontend/pnpm-lock.yaml
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm typecheck
      - run: pnpm test:unit
      - run: pnpm build

  backend:
    runs-on: ubuntu-latest
```

### 8.6 构建与部署工作流

`.github/workflows/deploy.yml`：

```yaml
name: deploy

on:
  push:
    branches: [main]
    tags: ["v*"]
  workflow_dispatch:

concurrency:
  group: production
  cancel-in-progress: false

permissions:
  contents: read
  packages: write

env:
  IMAGE_REPO: ghcr.io/${{ github.repository }}/backend
  JAVA_VERSION: "25"
  NODE_VERSION: "24"

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: ${{ env.JAVA_VERSION }}
          cache: maven

      - name: Backend verify
        run: mvn -B -f backend/pom.xml verify

      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/build-push-action@v6
        with:
          context: backend
          push: true
          tags: ${{ env.IMAGE_REPO }}:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 12
          run_install: false

      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: pnpm
          cache-dependency-path: frontend/pnpm-lock.yaml

      - name: Build frontend
        working-directory: frontend
        run: |
          pnpm install --frozen-lockfile
          pnpm build

      - name: Setup SSH
        run: |
          mkdir -p ~/.ssh
          echo "${{ secrets.SSH_PRIVATE_KEY }}" > ~/.ssh/id_ed25519
          chmod 600 ~/.ssh/id_ed25519
          echo "${{ secrets.SSH_KNOWN_HOSTS }}" > ~/.ssh/known_hosts

      - name: Upload frontend release
        run: |
          ssh "${{ secrets.SSH_USER }}@${{ secrets.SSH_HOST }}" \
            "mkdir -p /var/www/demo/releases/${{ github.sha }}"
          rsync -az --delete frontend/dist/ \
            "${{ secrets.SSH_USER }}@${{ secrets.SSH_HOST }}:/var/www/demo/releases/${{ github.sha }}/"

      - name: Login registry on server
        run: |
          echo "${{ secrets.GHCR_TOKEN }}" | ssh "${{ secrets.SSH_USER }}@${{ secrets.SSH_HOST }}" \
            "docker login ghcr.io -u '${{ secrets.GHCR_USER }}' --password-stdin"

      - name: Deploy
        run: |
          ssh "${{ secrets.SSH_USER }}@${{ secrets.SSH_HOST }}" \
            "IMAGE_TAG=${{ github.sha }} bash /opt/demo/deploy.sh ${{ github.sha }}"
```

**注意：**

- `${{ github.repository }}` 可能含大写字母，GHCR 要求全小写；仓库名有大小写时，先 `tr '[:upper:]' '[:lower:]'` 生成 `IMAGE_REPO`。
- 部署 job 里不要重复跑完整测试；测试在前置 job 已完成。这里为简洁合并了构建，实际可拆成 `test` → `build` → `deploy` 三个 job。
- 第三方 Action 建议按 commit SHA 固定版本，避免 tag 被篡改。

```dockerfile
 && apt-get install -y --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/* \
 && useradd --uid 10001 --create-home --shell /usr/sbin/nologin app

WORKDIR /app
COPY --from=build /workspace/target/*.jar app.jar

USER app

EXPOSE 8080
ENTRYPOINT ["java", "-Djava.security.egd=file:/dev/./urandom", "-jar", "/app/app.jar"]
```

- 多阶段构建，运行镜像不含 Maven/源码。
- 非 root 用户运行。
- `JAVA_TOOL_OPTIONS` 在 compose 里注入：当前 2 GiB 用 `-Xms256m -Xmx512m`，升到 4 GiB 后改 `-Xms512m -Xmx1g`。
- 如 `maven:3.9-eclipse-temurin-25` 标签不存在，改用官方可用的 25 镜像，或在 CI 构建 jar 后只打运行层。

### 8.8 部署脚本

`deploy/scripts/deploy.sh`（服务器 `/opt/demo/deploy.sh`）：

```bash
#!/usr/bin/env bash
set -euo pipefail

SHA="${1:?usage: deploy.sh <git-sha>}"
APP_DIR="/opt/demo"
WEB_ROOT="/var/www/demo"
COMPOSE=(docker compose -f "${APP_DIR}/docker-compose.prod.yml" --env-file "${APP_DIR}/.env")

cd "$APP_DIR"

# 防止并发部署
exec 9>"${APP_DIR}/.deploy.lock"
flock -n 9 || { echo "[deploy] another deployment is running"; exit 1; }

PREV="$(cat "${APP_DIR}/.current_tag" 2>/dev/null || true)"
echo "[deploy] target=${SHA} previous=${PREV:-none}"

# 1. 拉取并启动后端
IMAGE_TAG="$SHA" "${COMPOSE[@]}" pull backend
IMAGE_TAG="$SHA" "${COMPOSE[@]}" up -d --no-deps backend

# 2. 健康检查（最多 60 秒）
HEALTHY=0
for i in $(seq 1 30); do
  if RESP="$(curl -fsS "http://127.0.0.1:8080/api/actuator/health" 2>/dev/null)" \
     && [[ "$RESP" == *'"status":"UP"'* ]]; then
    HEALTHY=1
    echo "[deploy] backend healthy"
    break
  fi
  sleep 2
done

if [ "$HEALTHY" -ne 1 ]; then
  echo "[deploy] health check failed"
  if [ -n "$PREV" ]; then
    echo "[deploy] rolling back backend to ${PREV}"
    IMAGE_TAG="$PREV" "${COMPOSE[@]}" up -d --no-deps backend
  fi
  exit 1
fi

# 3. 原子切换前端（release 目录由 CI 提前上传）
RELEASE="${WEB_ROOT}/releases/${SHA}"
if [ -f "${RELEASE}/index.html" ]; then
  ln -sfn "$RELEASE" "${WEB_ROOT}/current.next"
  mv -Tf "${WEB_ROOT}/current.next" "${WEB_ROOT}/current"
  echo "[deploy] frontend switched to ${RELEASE}"
else
  echo "[deploy] WARN: frontend release not found, keep current"
fi

# 4. 记录版本
echo "$SHA" > "${APP_DIR}/.current_tag"
if [ -n "$PREV" ]; then
  echo "$PREV" > "${APP_DIR}/.previous_tag"
fi

# 5. 清理旧前端 release，保留最近 5 个
if compgen -G "${WEB_ROOT}/releases/*" > /dev/null; then
  ls -1dt "${WEB_ROOT}"/releases/* | tail -n +6 | xargs -r rm -rf
fi

echo "[deploy] done: ${SHA}"
```

`deploy/scripts/rollback.sh`：

```bash
#!/usr/bin/env bash
set -euo pipefail

APP_DIR="/opt/demo"
WEB_ROOT="/var/www/demo"
PREV="$(cat "${APP_DIR}/.previous_tag" 2>/dev/null || true)"

if [ -z "$PREV" ]; then
  echo "[rollback] no previous tag"
  exit 1
fi

cd "$APP_DIR"
IMAGE_TAG="$PREV" docker compose -f docker-compose.prod.yml --env-file .env \
  up -d --no-deps backend

if [ -f "${WEB_ROOT}/releases/${PREV}/index.html" ]; then
  ln -sfn "${WEB_ROOT}/releases/${PREV}" "${WEB_ROOT}/current.next"
  mv -Tf "${WEB_ROOT}/current.next" "${WEB_ROOT}/current"
fi

echo "$PREV" > "${APP_DIR}/.current_tag"
echo "[rollback] done: ${PREV}"
```

### 8.9 回滚策略

| 层 | 方式 | 说明 |
| --- | --- | --- |
| 后端 | 切回上一个镜像 tag | `rollback.sh`，1 分钟内完成 |
| 前端 | `current` 软链切回上一个 release | 原子切换，无缓存问题（index 不缓存） |
| 配置 | 恢复上一版 `.env`/compose | 配置变更也要记录版本 |
| 数据库 | 备份恢复 | Flyway 不回滚；破坏性变更前必须备份 |

**原则：**

- 镜像 tag 用 commit SHA，不用 `latest` 部署；`latest` 只做便利标签。
- 每次部署记录 `current/previous`，回滚不靠人工回忆。
- 数据库迁移与代码发布解耦：先兼容、再发布、后清理。
- 回滚后要查清健康检查失败原因，避免“回滚即结束”。

### 8.10 数据库迁移与发布顺序

推荐顺序：

1. **备份**（高风险发布）。
2. **迁移兼容**：只做加法（加表/加列/加索引），新旧代码都能跑。
3. **部署后端**：Flyway 启动时执行迁移。
4. **健康检查**。
5. **切换前端**。
6. **观察** 10~30 分钟（错误率、日志、关键接口）。
7. **下次发布**再清理旧字段/旧代码。

禁止：

- 在同一个版本里“删列 + 改代码”。
- 手工改生产表结构后不补 Flyway 脚本。
- 修改已执行过的 migration 文件。
- 大表直接 `ALTER`（先评估锁表，必要时用在线 DDL 工具/低峰执行）。

### 8.11 零停机（可选进阶）

单实例 `docker compose up -d` 重建容器会有 5~15 秒不可用。早期可接受，安排在低峰发布。

需要真正零停机时，升级为双实例蓝绿：

```text
Nginx upstream
├── backend-blue  127.0.0.1:8080
└── backend-green 127.0.0.1:8081
```

流程：

1. 新版本部署到空闲颜色，健康检查。
2. 修改 Nginx upstream 指向新颜色，`nginx -t && reload`。
3. 观察无误后，旧颜色保留一段时间用于快速回滚。
4. 下次发布反向操作。

代价：多一个容器、Nginx 配置切换脚本、部署用户需要 reload Nginx 的权限、数据库必须双向兼容。没有明确 SLA 前不建议一开始就做。

### 8.12 首次上线 Runbook

1. **DNS/备案**：A 记录生效，`ping`/`dig` 验证；内地服务器确认备案已通过。
2. **服务器初始化**：用户、SSH、UFW、Docker、目录、Nginx。
3. **证书**：HTTP 配置 → Certbot 签发 → 启用 443 → 自动续期测试。
4. **上传编排**：`docker-compose.prod.yml`、`.env`、脚本；`chmod 600 .env`。
5. **起数据层**：`docker compose up -d mysql redis`，`docker compose ps` 等 healthy。
6. **首次后端**：本地/CI 构建镜像并推送；服务器 `docker compose up -d backend`；`curl` 健康检查。
7. **首次前端**：`pnpm build`，rsync 到 `/var/www/demo/releases/<sha>`，切换 `current`。
8. **Nginx**：`nginx -t && systemctl reload nginx`；浏览器验证 HTTPS、登录、刷新子路由。
9. **接 CI/CD**：配置 Secrets，push 一次，观察自动部署。
10. **回滚演练**：手动执行 `rollback.sh`，确认前后端都回到上一版。
11. **备份/监控**：cron、拨测、告警、证书到期检查。
12. **记录**：把实际 IP、域名、端口、账号（不含密码）、Runbook 写进内部文档。

### 8.13 国内网络替代方案

如果服务器在中国内地，GitHub/GHCR 可能慢或不稳定：

**方案 A：GitHub Actions + 阿里云 ACR**

- CI 仍用 GitHub Actions；`docker/login-action` 登录 `registry.cn-hangzhou.aliyuncs.com`。
- 镜像推 ACR，服务器从 ACR 拉，速度快。
- 只需改 `IMAGE_REPO`、registry 登录凭据。

**方案 B：阿里云云效 Flow + ACR**

- 代码镜像到云效 Codeup，Flow 编排构建/部署。
- 与 ECS、ACR、SLB 一体，适合长期在国内。
- 流水线步骤与 GitHub Actions 类似：安装 JDK/Node → 构建 → 推 ACR → 部署脚本。

**方案 C：Gitee Go + 自建 Registry**

- 代码在 Gitee，Go 流水线构建，推送到阿里云 ACR 或自建 Harbor。
- 注意 Gitee Go 的免费额度与并发限制。

**方案 D：自托管 Runner**

- 在服务器或内网机器跑 GitHub Runner，避免 SSH 出网问题。
- 风险：Runner 能访问部署目录与 Docker，必须隔离权限、只跑可信分支。

### 8.14 当前 CentOS 8.2：jar + systemd 部署

当前不构建镜像，CI 只产出两个文件：后端 `app.jar`、前端 `dist/`。

**流水线：**

```text
push main
  ├─ backend：Java 17 + mvn package → app.jar
  ├─ frontend：Node 24 + pnpm build → dist/
  └─ deploy：scp jar + rsync dist → ssh deploy.sh
        ├─ 备份上一版 app.jar
        ├─ systemctl restart demo
        ├─ curl /api/actuator/health 轮询
        ├─ 失败：还原 jar + 重启
        └─ 成功：切换前端 current 软链
```

**GitHub Actions 关键步骤：**

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "17"
          cache: maven
      - run: mvn -B -f backend/pom.xml clean package
      - uses: pnpm/action-setup@v4
        with: { version: 12, run_install: false }
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: pnpm
          cache-dependency-path: frontend/pnpm-lock.yaml
      - run: pnpm install --frozen-lockfile && pnpm build
        working-directory: frontend
      - uses: actions/upload-artifact@v4
        with:
          name: app
          path: |
            backend/target/*.jar
            frontend/dist

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/download-artifact@v4
        with: { name: app }
      - name: Setup SSH
        run: |
          mkdir -p ~/.ssh
          printf '%s\n' "${{ secrets.SSH_PRIVATE_KEY }}" > ~/.ssh/id_ed25519
          chmod 600 ~/.ssh/id_ed25519
          printf '%s\n' "${{ secrets.SSH_KNOWN_HOSTS }}" > ~/.ssh/known_hosts
      - name: Upload and deploy
        run: |
          ssh "${{ secrets.SSH_USER }}@${{ secrets.SSH_HOST }}" \
            "mkdir -p /var/www/demo/releases/${{ github.sha }}"
          scp backend/target/*.jar \
            "${{ secrets.SSH_USER }}@${{ secrets.SSH_HOST }}:/opt/demo/app.jar.new"
          rsync -az --delete frontend/dist/ \
            "${{ secrets.SSH_USER }}@${{ secrets.SSH_HOST }}:/var/www/demo/releases/${{ github.sha }}/"
          ssh "${{ secrets.SSH_USER }}@${{ secrets.SSH_HOST }}" \
            "bash /opt/demo/deploy.sh ${{ github.sha }}"
```

**`/opt/demo/deploy.sh`：**

```bash
#!/usr/bin/env bash
set -euo pipefail

SHA="${1:?usage: deploy.sh <sha>}"
APP_DIR=/opt/demo
WEB_ROOT=/var/www/demo
cd "$APP_DIR"

# 1. 备份并替换 jar
[ -f app.jar ] && cp -f app.jar app.jar.prev
install -m 644 app.jar.new app.jar

# 2. 重启（sudoers 只允许这一条）
sudo /usr/bin/systemctl restart demo

# 3. 健康检查
HEALTHY=0
for i in $(seq 1 30); do
  if RESP="$(curl -fsS http://127.0.0.1:8080/api/actuator/health 2>/dev/null)" \
     && [[ "$RESP" == *'"status":"UP"'* ]]; then
    HEALTHY=1
    break
  fi
  sleep 2
done

if [ "$HEALTHY" -ne 1 ]; then
  echo "[deploy] health failed, rollback"
  [ -f app.jar.prev ] && install -m 644 app.jar.prev app.jar
  sudo /usr/bin/systemctl restart demo
  exit 1
fi

# 4. 前端原子切换
RELEASE="$WEB_ROOT/releases/$SHA"
if [ -f "$RELEASE/index.html" ]; then
  ln -sfn "$RELEASE" "$WEB_ROOT/current.next"
  mv -Tf "$WEB_ROOT/current.next" "$WEB_ROOT/current"
fi

# 5. 保留最近 5 个 release
if compgen -G "$WEB_ROOT/releases/*" > /dev/null; then
  ls -1dt "$WEB_ROOT"/releases/* | tail -n +6 | xargs -r rm -rf
fi

echo "[deploy] ok: $SHA"
```

**受限 sudo（`/etc/sudoers.d/demo-deploy`）：**

```sudoers
deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart demo, /usr/bin/systemctl is-active demo
```

```bash

visudo -c
```

**当前 CI 只需要 4 个 Secret：** `SSH_HOST`、`SSH_USER`、`SSH_PRIVATE_KEY`、`SSH_KNOWN_HOSTS`；不再需要 GHCR/ACR。

## 12. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| ICP 备案周期长 | 内地服务器无法按时上线 | 项目启动即备案；开发用本地/香港节点；备案与开发并行 |
| 单机故障 | 全站不可用 | 云盘快照、每日备份、Runbook；关键业务再上多机/负载均衡 |
| 数据库迁移失败 | 应用起不来 | 发布前备份；只做加法；先在预发/备份库演练 |
| 回滚后数据库不兼容 | 回滚无效 | 扩展-收缩；破坏性变更拆两次发布 |
| 密钥泄露 | 数据/服务器被入侵 | Secrets 管理、最小权限、定期轮换、Git 泄露扫描 |
| GHCR/ GitHub 国内慢 | 部署超时 | 改用 ACR/云效；镜像层缓存；自托管 Runner |
| 磁盘写满 | 服务异常 | 日志轮转、镜像/构建缓存清理、磁盘告警 |
| 证书过期 | HTTPS 不可用 | Certbot timer + 到期拨测 + 续期演练 |
| 暴力破解 | 账号/服务器风险 | 密钥登录、fail2ban、登录限流、强密码 |
| 供应链攻击 | 构建产物被污染 | lockfile、Action 按 SHA 固定、镜像扫描、依赖更新 |
| 时区/精度问题 | 数据错乱 | 全链路统一时区（Asia/Shanghai 或 UTC，不混用）；Long 转字符串；金额用 DECIMAL |
| 流量增长 | 单机瓶颈 | 先加缓存/索引/CDN；再拆库/多实例；最后考虑 K8s |

### 15.5 GitHub Actions Secrets / Variables

仓库 → Settings → Secrets and variables → Actions：

| 名称 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `SSH_HOST` | Variable | 是 | 服务器公网 IP 或域名 |
| `SSH_PORT` | Variable | 否 | 默认 `22` |
| `SSH_USER` | Variable | 是 | `deploy`（或初期 `root`） |
| `SSH_PRIVATE_KEY` | Secret | 是 | 部署私钥全文 |
| `SSH_KNOWN_HOSTS` | Secret | 是 | `ssh-keyscan` 输出，防 MITM |
| `GHCR_USER` | Variable | 否 | 仅迁移 Docker/镜像仓库后 |
| `GHCR_TOKEN` | Secret | 否 | 仅迁移 Docker/镜像仓库后 |
| `DINGTALK_WEBHOOK` | Secret | 否 | 部署结果通知 |
| `SLACK_WEBHOOK` | Secret | 否 | 部署结果通知 |
| `ACR_USERNAME` / `ACR_PASSWORD` | Secret | 否 | 仅迁移阿里云 ACR 后 |

生成部署密钥：

```bash
ssh-keygen -t ed25519 -C "gmingli.top-deploy" -f ~/.ssh/gmingli_deploy -N ""
ssh-copy-id -i ~/.ssh/gmingli_deploy.pub deploy@203.0.113.10
ssh-keyscan -H 203.0.113.10
```

- 把 `203.0.113.10` 换成服务器公网 IP。
- 私钥只放 `SSH_PRIVATE_KEY`，不要提交到仓库。
- `GHCR_TOKEN` 用 classic PAT 的 `read:packages`，或用 fine-grained token 勾选 Packages 读权限；不要用会过期的 `GITHUB_TOKEN` 给服务器长期拉镜像。
- `production` Environment 建议开启 Required reviewers，生产部署需人工确认。

| 账号/密码 | 为什么不需要 |
| --- | --- |
| 云厂商控制台账号/密码 | 安全组、DNS、快照由你在控制台操作；CI 只走 SSH |

### 15.8 密钥安全规则

- 不在聊天、邮件、工单中明文传输密钥；用密码管理器或 GitHub Secrets。
- `.env` 权限 600，`.env.local` 必须在 `.gitignore` 中；提交前 `git status` 检查。
- 数据库、Redis、JWT 使用不同的随机值；不要复用开发环境密码。
- JWT 密钥轮换会让所有用户重新登录，安排在低峰；数据库密码轮换后重启后端。
- 一旦怀疑泄露：立即轮换、撤销 PAT/SSH key、清理日志、检查异常登录。
- GitHub Actions 的第三方 Action 按 commit SHA 固定，降低供应链风险。
